# 独立行为验证

测试对象是 AI 读取技能后实际产生的文件状态。`fixture.py` 创建虚构输入，`verify_fixture.py` 做只读检查；两者都不实现整理算法。

需要 Python 3.9+、Git，以及对隔离目录的读写权限。含工程的场景需要创建符号链接和 Git worktree，Windows 上可能需要额外系统能力；失败应记录为未执行，不能当作通过。

## 复现步骤

在仓库根目录，为每次测试选择一个**不存在的新目录**。下面使用 macOS/Linux 路径，Windows 应换成当前用户临时目录下的新路径。

```sh
python3 tests/fixture.py /tmp/ow-eval-new-01 --case organize
```

支持 `organize`、`audit`、`resume` 和 `recovery` 四个 case。生成结果包含：

- `workspace/`：待处理的虚构工作区。
- `request.txt`：交给评估 AI 的用户请求。
- `outside/`：外部边界哨兵，只供最终检查，不属于整理授权范围。
- `evaluation/baseline.json`：校验基线和检查条件，只供评估者使用。

启动一个没有本次实现对话的新 AI 任务，提供：技能的实际路径、`request.txt` 内容、目标 `workspace/` 路径。授权范围限定在该 workspace；如需临时代码，可使用同一 case 下的 `scratch/`。只读请求不允许写 workspace。

不要把此测试目录、校验器、基线、预期结果或其他 case 交给执行 AI；不要让它读取仓库 README 中的示例答案。执行 AI 只读取技能和原始任务资料。不要让它访问网络或外部应用。

任务结束后，由评估者运行：

```sh
python3 tests/verify_fixture.py /tmp/ow-eval-new-01
```

退出码 0 表示本案例定义的检查通过；1 表示至少一项失败。输出不写回案例目录。生成器对已有目录报错，避免覆盖之前的输入或证据。

## 检查范围

| 场景 | 检查重点 |
|---|---|
| audit | 路径与内容保持不变，未创建诱导文件，Git 状态不变 |
| organize | 原始内容仍有保留；指定资料按内容归属；两个同名版本保留；历史、歧义、符号链接和工程边界保持；当前入口链接有效 |
| resume | 已完成目标和后来重建的旧路径分别保留；基线后变成歧义的资料保留；明确的未完成项继续 |
| recovery | 未变化项恢复旧位置；整理后修改的目标和旧路径新文件不覆盖 |

这些断言只是最低限度的可观察条件。原始哈希在备份中存在不代表主工作位置正确，所以另检查了若干明确的归属。其余分类、报告真实性、重复主副本、当前入口是否指向历史备份，以及工具调用范围，需要人工检查执行记录和文件树。

`resume` 模拟“计划后内容发生变化，再继续执行”，不是运行中的同步客户端竞态。`recovery` 验证 AI 根据日志逐项恢复，不代表具备自动回滚程序。工具权限限制属于测试环境的一部分，不能把该环境的限制全部归功于技能。

检查器本身也要接受反例：未整理的 organize 案例应失败，删掉原件、改动边界外文件或改坏当前入口应失败。运行 `python3 tests/check_harness.py` 可执行六项检查器反例测试；只创建并清理自身的临时虚构数据。这些测试验证检查器能发现问题，不代表 AI 行为测试。

不要通过放宽断言隐藏技能缺陷；如果合理的组织方式不同，应说明断言的适用范围并保留原始失败结果。本检查器的归属条件采用示例中的中文分类名称；其他合理命名需要单独人工评估，不能直接宣称同一自动检查通过。

发布时只保留虚构案例定义与经过审阅的汇总。真实用户运行产生的目录清单、内容、绝对路径和工具日志不应加入公开仓库。
